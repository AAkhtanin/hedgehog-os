# Root-Centered Needle Geometry

## Purpose

Hedgehog OS must not be reduced to:

```text
Root -> Orchestrator -> Architect -> Executor -> Validation -> GT -> Root
```

That trace is one flat observable projection. The architecture is a
Root-centered geometry of bounded directed capabilities.

Public first formula:

> Hedgehog OS is a Root-controlled runtime where AI capabilities compose safely
> without turning models, tools, memory, or external services into authority.

Russian variant:

> Hedgehog OS — это Root-controlled runtime, где AI-способности могут безопасно
> сцепляться вокруг Root, не превращая модели, инструменты, память или внешние
> сервисы во власть.

Do not lead public explanations with "multidimensional Internet of Meaning."
Start with Root authority and safe capability composition.

## Root

Root is the point of sovereignty and the only final commit boundary in its
contour. Root:

- holds final authority;
- creates and commits FinalOutput;
- authorizes writes upward;
- authorizes promotion and reuse;
- authorizes quarantine release and deadend override;
- authorizes local installation of capabilities.

Core authority rule:

> Vassal of my vassal is not my vassal.

A child cell or nested capability may hold bounded local authority. That
authority does not automatically propagate upward, sideways, outward, or into
Root.

## Needles

A needle is not a plugin. It is a directed bounded capability / capability
contract anchored in Root.

A needle may be simple or complex. A complex needle may contain a local
Orchestrator / Architect / Executor rhythm, PlanGraph, DAG, child cells,
validators, local memory, or local checks. It may return evidence, proposals,
or boundary artifacts. It never becomes Root.

Canonical execution and needles are related but distinct:

- **Canonical execution** is the main downward Root-controlled runtime vector.
- **Needle** is a bounded capability contract / directed semantic organ that
  may participate inside canonical execution or another Root-governed
  direction.
- **Marennya and UP** are systemic/internal needle-like directions, not
  mandatory initial runtime components.

Canonical execution must not be described as merely one ordinary needle.

## Geometric Directions

### Downward Canonical Execution Vector

```text
User/Event
-> WorldState
-> DRS retrieval
-> AVF / AttractorPacket
-> Architect PlanGraph
-> DAG / NeedleRuntime / ChildCell
-> ResultProposal
-> Post V&V
-> GT
-> Root Final
-> DRS Lifecycle
-> ConflictCheck
-> audit / hash-chain
```

This is the main applied runtime direction. It is Root-controlled throughout,
even when bounded capabilities or child cells execute locally.

### Lateral Marennya

Marennya is a reflective systemic/internal needle-like direction. It may
propose patches, deadend candidates, validator patches, protocol candidates,
risk notes, and reuse corrections.

Marennya produces proposals only. It is quarantine-first, cannot mutate Work,
cannot install needles, cannot create FinalOutput, and requires Root approval.

### Upward UP

UP is a transfer/opportunity systemic/internal needle-like direction. It may
propose transfer candidates, opportunity reports, and higher-level pattern
candidates.

UP produces proposals only. It is quarantine-first, cannot mutate Work, cannot
install needles, cannot create FinalOutput, and requires Root approval.

Marennya and UP are important but deferred. They are not required for the first
applied semantic demos and may remain stubs for a long time. The architecture
must allow other future systemic reflective needles; Marennya and UP are not an
exhaustive list.

## DRS Topology

DRS is not a memory database, vector store, or authority. DRS is semantic
topology and an address / resonance / lineage / audit / trust / TTL / conflict
/ reuse / promotion fabric.

DRS turns traces of capabilities into addressable semantic evidence. Dense
artifacts remain outside DRS and are referenced through pointers. DRS can
connect needles and experiences through semantic resonance, deadends, trust,
lineage, conflict flags, reuse candidates, protocol candidates, and promotion
candidates.

DRS does not decide. Root remains commit authority.

## External DRS

External DRS is not a marketplace. It is controlled transfer of verified
meaning traces between Root-governed systems. External experience is candidate
influence, not authority.

```text
External Root proof pointer
-> provenance / trust / GT / ConflictCheck / policy
-> local adaptation
-> protocol_candidate
-> NeedleCandidate
-> Root-approved local installation
```

No external pointer, reputation signal, or transferred experience can install a
local capability without Root approval.

## Applied Fractal Geometry Checkpoint

One-parent controlled Fractal DAC geometry is:

```text
parent request
  -> bounded local child-cell candidates
  -> local proposals
  -> Root aggregation
  -> Root final
```

Child-cell candidates are local proof-mode structures, not real autonomous
agents. They cannot finalize the parent, execute actions, write DRS, install
Needles, spawn children, override siblings, or create protocol/NeedleCandidate
objects.

Dual coupling geometry is:

```text
parent DAC <-> bounded semantic coupling edges <-> parent DAC
```

Coupling edges transfer no authority, finalization, execution, or DRS write.
Shared evidence can inform but cannot decide. Root remains sovereign and keeps
separate parent finals.
